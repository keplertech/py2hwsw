# RTL sequential equivalence checking of py2hwsw cores with kepler-formal

This directory reproduces two formal verification results on `iob_axi2iob`, the
AXI4 to IOb bridge from the py2hwsw library, using
[kepler-formal](https://github.com/keplertech/kepler-formal), an open-source
(Apache-2.0) equivalence checker developed by [keplertech.io](https://keplertech.io).

kepler-formal's RTL SEC mode compares the sequential behavior of two versions of
a design at their top-level ports. It returns one verdict: proved, or a
counterexample trace showing an input sequence for which the outputs differ.

Nothing outside this directory is modified. The scripts read the repository
history to generate each version of the core.

## Results

| Commit | Change | Intended effect | Verdict | Checked outputs | Proof time |
| --- | --- | --- | --- | --- | --- |
| e0434c789 (2025-01-17) | Quartus warning cleanup: adds `AXI_LEN_WIDTH`, removes unused `*prot` wires | Behavior unchanged | **Proved equivalent** (default parameters) | 127/127 | 23 s |
| 2d734efb2 (2024-12-20) | Fix of the rvalid/rdata register enables | Behavior change | **Counterexample**: `s_axi_arready_o` differs at cycle 8 | 127/127 | 2 s |

Proof times exclude py2hwsw generation. They were measured on a 2-core Linux
machine with kepler-formal built from source (commit 46113b2, naja 0.7.33).

For the fix, the counterexample trace goes through the `iob_rvalid` register,
which is the register the commit changed. A counterexample is the expected
outcome here: it shows that the fix did change observable behavior, and where.

## How the comparison is set up

For each commit `C`, `sec_commit.sh`:

1. creates two git worktrees, one at `C^` (design 1) and one at `C` (design 2);
2. runs `py2hwsw iob_axi2iob setup --no_verilog_lint` with each worktree's own
   py2hwsw, so each side uses the framework and the generated submodules
   (`iob_reg`, `iob_reg_r`, `iob_reg_re`) of its own commit. Setup runs from a
   directory that holds only that side's output, because py2hwsw also looks up
   cores under the current directory;
3. stops if the two generated trees are identical, since the comparison would
   then be trivial, and otherwise lists the files that differ;
4. runs kepler-formal RTL SEC between the two generated `hardware/src` trees.

Settings:

- **RTL SEC, binary encoding.**
- **Reset bootstrap:** `arst_i` held at 1 for 4 cycles, then released. The
  bridge's registers get their initial value from this asynchronous reset.
  Without the bootstrap, kepler-formal reports "unsupported": it does not
  compare outputs that depend on state it cannot anchor to a known value.
- **Engines:** PDR (unbounded proof) for the cleanup; k-induction with
  max_k 8 for the fix, since a counterexample is found by the bounded search.
- **Parameters:** default values, as instantiated by `py2hwsw setup`.

One file is added to each generated tree, identically on both sides: an empty
`iob_bsp.vh`. It is a board header normally generated by the parent SoC. The
library registers include it but use none of its macros.

## Prerequisites

### kepler-formal

The RTL SEC reset bootstrap (`--sec-reset-port`) is a command-line option. The
`kepler-formal` package on PyPI provides the Python API only, so install the
command-line tool.

With Nix (binary cache):

```bash
nix run nixpkgs#cachix -- use keplertech
nix profile install 'git+https://github.com/keplertech/kepler-formal?ref=main&submodules=1#kepler-formal'
```

Or build from source with CMake (Ubuntu):

```bash
sudo apt-get install g++ cmake libboost-dev python3-dev capnproto libcapnp-dev \
  libtbb-dev pkg-config bison flex libspdlog-dev libfmt-dev \
  libboost-iostreams-dev zlib1g-dev
git clone --recurse-submodules https://github.com/keplertech/kepler-formal.git
cmake -S kepler-formal -B kepler-formal/build -DCMAKE_BUILD_TYPE=Release
make -C kepler-formal/build -j"$(nproc)" kepler-formal
export KEPLER_FORMAL=$PWD/kepler-formal/build/src/bin/kepler-formal
```

See the [kepler-formal README](https://github.com/keplertech/kepler-formal#build-instructions)
for macOS and Bazel builds.

### py2hwsw generation

`py2hwsw setup` only needs Python and the packages of `pythonEnv` in
`py2hwsw/lib/default.nix`. Either run the scripts inside the repository's
`nix-shell`, or use a virtual environment:

```bash
python3 -m venv .venv
.venv/bin/pip install -r keplertech/requirements.txt
export PYTHON=$PWD/.venv/bin/python
```

`verible` is not needed. When `verible-verilog-format` is not installed,
`sec_commit.sh` puts a no-op formatter on `PATH`, so generation only skips code
formatting, which does not change the RTL.

### Repository history

The scripts need the two commits and their parents. A clone made with
"copy the main branch only" has them; a shallow clone (`--depth 1`) does not.

## Running

From the repository root:

```bash
keplertech/run_all.sh
```

Expected end of output:

```
== iob_axi2iob: e0434c789^ (design 1) vs e0434c789 (design 2)
   ...
   No difference was found. SEC proved equivalence at k = 5.
   verdict: proved (exit 0)
   PASS: e0434c789 cleanup proved equivalent

== iob_axi2iob: 2d734efb2^ (design 1) vs 2d734efb2 (design 2)
   ...
   s_axi_arready_o[0]: design0=1, design1=0
   verdict: counterexample (exit 3)
   PASS: 2d734efb2 fix reported as a behavior change
```

Generated trees and logs go to `keplertech/work/` (ignored by git). Each run
writes the full kepler-formal log, including the complete counterexample trace,
to `keplertech/work/<core>_<commit>/kepler-formal.log`.

## Checking another core or commit

```bash
keplertech/sec_commit.sh <core> <commit> [engine] [max_k]
```

`engine` is `pdr` (default), `k_induction` or `imc`; `max_k` defaults to 32.
`RESET_PORT` (default `arst_i=1`) and `RESET_CYCLES` (default 4) set the reset
bootstrap. The exit code is kepler-formal's SEC exit code: 0 proved, 1 partially
proved, 2 inconclusive, 3 counterexample.

Requirements on the two versions:

- the top-level port names must be identical; internal names may change freely;
- cores that include generated headers other than `iob_bsp.vh` from a parent
  core may need those headers to be provided the same way.

## Possible use in CI

The same check can run on each change to a library core: generate the core at
the base and head of a pull request, then run kepler-formal RTL SEC. A refactor
or a lint fix is expected to prove equivalent; an intended behavior change shows
up as a counterexample with a trace, which documents exactly what changed.
